# 测试

```powershell
go test ./...                    # 全部测试，含三条架构红线与 gofmt 闸门
```

这一条就够了：红线与格式闸门都在 `internal/archtest` 里，随 `go test ./...` 自动执行，不依赖 `make`。

## 有 make 时还有这些

| 命令 | 作用 |
|---|---|
| `make test-e2e` | 端到端（含跨网段收敛） |
| `make test-scale` | 20 节点规模验证 |
| `make test-fuzz` | 协议畸形输入 |
| `make lint-arch` | 架构红线 + 格式闸门 |
| `make ci` | 等价于 CI 的一条命令 |

## 测试矩阵

| 层级 | 范围 | 目标 |
|---|---|---|
| 单元 | `domain/**` | 覆盖率 ≥ 80% |
| 组件 | 协议编解码 / SQLite 迁移 | 无 panic、迁移可重入 |
| 集成 | 2 节点握手与会话管理 | 主链路通过 |
| E2E | 3~4 节点全链路、跨网段收敛 | 通过 |
| 规模 | 20 节点 | 目录同步正确、常驻连接 0 |
| 前端 | 类型检查与构建 | 通过 |

## 为什么测试里没有 `time.Sleep`

测试用 `FakeClock` 控制系统时间：心跳超时（30 s）、TTL（300 s）、空闲回收（5 min）。若用真实时间，一个用例要跑几分钟；有了 `Clock` 接口，这些全部是微秒级。

这不是为了跑得快，而是为了让**超时相关的分支可测** —— 真实时钟下没人愿意为一个「300 秒后过期」写用例。

## 规模测试在验证什么

20 个节点时检查两件事：目录同步结果正确，以及**常驻连接数为 0**。后者是架构约束的直接体现：空闲连接会被回收，不是靠连接池硬撑。
